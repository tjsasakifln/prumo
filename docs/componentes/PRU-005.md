# PRU-005: SQLite, ZIP e continuidade do projeto local

**Pesquisa e exame de pacotes:** 14/11/2026. **Estado:** escolha de componentes, ensaios isolados, auditoria do lock, revisão dos contratos de recuperação, verificação integrada local e empacotamento concluídos. A integração depende dos checks do PR para o mesmo código. Esta ficha qualifica o recorte de persistência, sem atribuir aprovação a cálculos de engenharia.

## 1. Decisão e responsabilidade do adaptador

A persistência passa a exigir duas propriedades diferentes: transações locais durante a edição e um pacote transportável que contenha o projeto e suas dependências. O banco precisa publicar uma revisão completa ou conservar a anterior. O pacote precisa declarar versão, identidade, conteúdo, hashes e limites, e reabrir sem rede. Uma biblioteca de compressão não define essas regras; um banco transacional não torna atômica, por si só, a publicação de outro arquivo.

A escolha é **rusqlite 0.42.0 com SQLite 3.54.1 incorporado** e **zip 9.5.1 com Stored/Deflate**. O serviço Rust continua sendo a única autoridade de mutação. SQLite é um componente externo em C, acessado pelo binding Rust qualificado; não há lógica própria do produto em outra linguagem.

```toml
rusqlite = { version = "=0.42.0", default-features = false, features = ["bundled", "backup", "limits", "hooks"] }
zip = { version = "=9.5.1", default-features = false, features = ["deflate-flate2-zlib-rs"] }
```

Em rusqlite, `bundled` fixa a implementação SQLite distribuída, `backup` fornece a cópia consistente do banco em uso, `limits` expõe limites por conexão e `hooks` permite autorização e interrupção de consultas. Esta última também habilita a API de WAL. Não foram selecionados cache de statements, backend SQLite para navegador, funções SQL próprias, tabelas virtuais próprias, SQLCipher, carregamento de extensões, geração de bindings no build ou conversores adicionais de data e JSON.

Em zip, a feature escolhida habilita Deflate pelo backend Rust de flate2/zlib-rs. Evita o grupo padrão, que também ativa algoritmos e recursos desnecessários ao formato. Não se habilitaram AES, Zopfli, Bzip2, Deflate64, LZMA, XZ, PPMd, Zstd ou integração com relógio. Isso não substitui a recusa explícita de entradas criptografadas ou de métodos fora do perfil na leitura.

## 4. Transações, backup e continuidade

A [documentação de WAL](https://sqlite.org/wal.html) distingue a confirmação no journal da incorporação das páginas ao arquivo principal. Assim, copiar somente o `.db` de uma conexão ativa pode produzir um arquivo consistente, porém antigo. A prova isolada desta revisão reproduziu exatamente essa diferença. Exportação e backup precisam usar uma fotografia consistente, não uma cópia bruta escolhida pela extensão do arquivo.

A [API de backup](https://sqlite.org/backup.html) permite copiar o estado visível da origem para outra conexão. No adaptador, a cópia de destino deve ser concluída, validada e fechada antes de entrar no pacote. `Backup::run_to_completion` repete `Busy` e `Locked` sem prazo próprio; um fluxo que precise ser limitado deve controlar `Backup::step` e seu prazo ou tratar a recusa de bloqueio explicitamente. O tipo de backup impede acesso Rust normal à conexão de destino enquanto ela está emprestada pela operação.

O adaptador implementa `journal_mode=DELETE` e `synchronous=EXTRA`, com consulta da configuração após defini-la. EXTRA sincroniza também o diretório após a remoção do journal. `synchronous=FULL` atende ao contrato de WAL, mas com rollback journal pode perder o último commit depois de queda de energia, sem corromper o banco. A [documentação do pragma](https://sqlite.org/pragma.html#pragma_synchronous) e as [hipóteses de commit atômico](https://sqlite.org/atomiccommit.html) também deixam claro que a garantia depende das operações de sincronização e do sistema de arquivos. Encerrar um processo em teste comprova recuperação daquele tipo de falha; não equivale a desligar a máquina ou ensaiar todo hardware possível. O ensaio de WAL desta ficha é uma contraprova da cópia bruta, não a configuração do banco de trabalho entregue.

O commit do banco e a substituição do pacote são operações distintas. Se a interrupção ocorrer entre ambas, o estado confirmado no banco precisa continuar identificável e recuperável. O protocolo do Prumo deve distinguir revisão salva no banco, revisão publicada e candidato de recuperação, preservando origem e hashes. Um erro de exportação não pode aparentar sucesso completo nem destruir a última revisão íntegra.

A leitura também tem efeitos de plataforma a considerar: um banco em WAL pode precisar dos arquivos `-wal` e `-shm`. A opção `immutable=1` é apropriada apenas para uma cópia efetivamente congelada; usá-la em uma autoridade ainda mutável pode ocultar alterações. Abrir ou diagnosticar em modo de leitura não deve criar estado persistente no projeto, e o uso em diretório sem escrita precisa de teste próprio.

## 5. Banco recebido e recursos limitados

Um banco dentro de um pacote deve ser tratado como entrada externa. A [orientação oficial de segurança](https://sqlite.org/security.html) recomenda reduzir a superfície de execução e impor limites. A configuração examinada expõe `DEFENSIVE`, `TRUSTED_SCHEMA`, `ENABLE_TRIGGER`, `ENABLE_VIEW`, limites por conexão, authorizer e progress handler.

O contrato desta etapa não precisa executar views, triggers ou SQL arbitrário. A defesa inclui desativar esses caminhos quando não utilizados, conferir integridade e esquema, limitar memória/tamanho/tempo e confrontar versão e identidade antes de ler os dados de engenharia. As consultas e comandos usam SQL estático e parâmetros. Não se deve transformar uma tabela chamada como a esperada em evidência de esquema correto.

O modo defensivo não é verificação semântica do projeto. Ainda é necessário conferir hashes de objetos, relações, envelopes de revisão, snapshots e resultados no domínio. Da mesma forma, um hash identifica conteúdo e detecta divergência; não é assinatura profissional nem autenticação criptográfica do autor.

## 6. Perfil ZIP e dados futuros

A referência estrutural usada no ensaio é a [APPNOTE 6.3.10 da PKWARE](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT), sem reproduzir a publicação no repositório. A biblioteca declara seu perfil geral baseado na revisão 6.3.9. O Prumo precisa de um subconjunto explícito, com limites próprios de pacote, entradas, tamanho individual, total expandido e razão de expansão.

O exame do fonte identificou obrigações concretas do adaptador:

- `ZipArchive` armazena nomes em um mapa e conserva apenas uma entrada por nome para a enumeração usual. A recusa de duplicatas precisa de `has_duplicate_names()`, além de detectar colisões segundo a política de nomes do formato.
- `ZipReadOptions::enforce_header_consistency(true)` é necessário para confrontar os cabeçalhos local e central. A opção não está ligada por padrão.
- `has_overlapping_entries()` confere sobreposição envolvendo cabeçalhos e dados. O offset e os limites do diretório também precisam corresponder ao perfil admitido.
- `ZipArchive::offset() == 0` não prova ausência de prefixo: quando os offsets gravados já incluem os bytes anteriores ao primeiro cabeçalho, a biblioteca não precisa aplicar uma correção. Um ensaio independente confirmou `offset() == 0` e primeiro cabeçalho no byte 9. O perfil sem prefixo precisa conferir o início real dos cabeçalhos locais.
- O construtor não recebe um limite de quantidade de arquivos. A conferência prévia do tamanho do arquivo e dos campos de diretório impede reservar memória com base em contagens arbitrárias antes de validar o perfil.
- A leitura deve contabilizar os bytes efetivamente produzidos, exigir término válido e verificar CRC e SHA-256. O tamanho declarado no cabeçalho não substitui essa contagem.

Os nomes não são caminhos de extração. Entradas absolutas, `..`, prefixos de unidade ou rede, barras invertidas, NUL, fluxos alternativos de Windows, links e colisões devem ser recusados pelo perfil, sem sanitização silenciosa. O adaptador lê entradas aprovadas para destinos internos definidos por ele; não aplica permissões de arquivos recebidos. O formato não depende de `extract()`.

O escritor utiliza Stored para todas as entradas. Dados muito repetitivos podem ultrapassar a razão máxima mesmo sendo legítimos; essa escolha evita criar um pacote nativo que o próprio leitor recuse pela razão de compressão. A leitura admite Stored e Deflate. Limites são parte do contrato versionado e precisam de diagnóstico, não descarte parcial.

O perfil implementado limita o pacote a 128 MiB, o banco, cada entrada e a soma das extensões opacas a 64 MiB, a expansão total a 256 MiB, o manifesto a 2 MiB, a quantidade de entradas a 4.096 e a razão expandido/compactado a 200. O serviço conserva o limite anterior de 16 MiB para a representação JSON do projeto. O banco limita o diário a 2.048 registros e a leitura acumulada dos campos históricos a 512 MiB. A conferência de diretório ocorre antes da construção de `ZipArchive`; ZIP64, múltiplos discos, comentários, prefixos e caudas fora do perfil são recusados. Esses limites não são promessa de desempenho para qualquer modelo dentro deles.

Extensões opacas declaradas e limitadas podem ser conservadas sem interpretar sua semântica. Uma versão futura ou capacidade obrigatória desconhecida precisa bloquear a transformação que não consegue preservar seu significado. Não se deve ignorar propriedades desconhecidas, reconstruir apenas as conhecidas e publicar uma versão aparentemente válida. A migração conserva a cópia original; recuperação antiga não pode substituir silenciosamente um arquivo mais novo incompatível.

### Números JSON desconhecidos

A serde_json 1.0.154 já adotada mantém `float_roundtrip` e passa a habilitar também `arbitrary_precision`. As duas opções têm finalidades distintas: a primeira conserva o percurso `f64 → JSON → f64`, enquanto a segunda conserva a precisão dos números que entram como JSON e cujo significado o domínio atual desconhece. O [manifesto e a relação de features da publicação](https://docs.rs/crate/serde_json/1.0.154/features) não adicionam dependências para essa opção.

A contraprova executada mostrou que apenas `float_roundtrip` arredondava `18446744073709551617` e `0.12345678901234567890123456789` ao construir um `Value`. Com as duas opções, os dígitos são preservados na migração e nas edições. A normalização canônica de zero examina a mantissa textual, impedindo que `1e-9999` se torne zero por underflow. Um sinal positivo de expoente pode ficar explícito, como `1e9999` para `1e+9999`; não se promete conservar todo lexema numérico na projeção, mas sua precisão e a cópia byte a byte do original.

O exame do fonte também identificou que a biblioteca usa um marcador privado para transportar esses números. Chaves externas no namespace `$serde_json::private::` são recusadas antes de desserializar valores genéricos, inclusive com escapes Unicode. A recusa é uma incompatibilidade explícita, sem transformar o objeto nem habilitar a recuperação de versão antiga sobre ele. Strings de valor e blobs opacos podem conter o mesmo texto. A guarda é comum ao domínio, aos JSONs conhecidos do arquivo/banco e à entrada MCP; a biblioteca continua responsável pela sintaxe JSON. Os testes de domínio e `storage_precision.rs` cobrem precisão, snapshots, original preservado e essa distinção.

## 7. Segurança, licença e manutenção

Há uma razão concreta para não usar o `libsqlite3-sys 0.37.0` que já estava no cache local. O aviso [RUSTSEC-2026-0459](https://rustsec.org/advisories/RUSTSEC-2026-0459.html) afeta SQLite incorporado anterior a 3.54.0: abrir uma combinação maliciosa de banco e WAL pode expor memória não inicializada. O intervalo corrigido começa em libsqlite3-sys 0.39.0. A escolha 0.40.0 contém SQLite 3.54.1. A presença de uma versão no cache não constitui qualificação.

Os avisos de ZIP [RUSTSEC-2026-0367](https://rustsec.org/advisories/RUSTSEC-2026-0367.html), [0368](https://rustsec.org/advisories/RUSTSEC-2026-0368.html), [0369](https://rustsec.org/advisories/RUSTSEC-2026-0369.html) e [0429](https://rustsec.org/advisories/RUSTSEC-2026-0429.html) tratam de permissões, links e alocação excessiva na extração; a versão 9.5.1 escolhida contém as correções. A versão escolhida não justifica remover os limites ou aceitar extração arbitrária.

Rusqlite, seu binding e zip possuem textos MIT na publicação. Eles permitem distribuição comercial com preservação dos avisos aplicáveis. O núcleo SQLite possui [dedicação ao domínio público](https://sqlite.org/copyright.html), diferente da licença do binding. O cabeçalho de dedicação do código C e a identidade da versão devem aparecer na evidência de distribuição, sem chamar todo o conjunto de MIT. Não se incorporam SQLCipher, OpenSSL ou código de algoritmos opcionais por inferência a partir do README.

`cargo deny --locked check advisories licenses sources` passou para esse lock com a base RustSec no commit `4ef2df8e806a65e2f1ecc14f56f51249062b23d6`: `advisories ok, licenses ok, sources ok`. A geração de avisos e `scripts/generate_notices.py --check` também passaram. Não foi criada exceção para vulnerabilidade ou licença nesta etapa.

As quatro exceções informativas de manutenção herdadas foram reexaminadas e mantidas no mesmo escopo: RUSTSEC-2026-0370, 0371 e 0372 para a cadeia de acessibilidade AccessKit/AT-SPI com zbus 5, e RUSTSEC-2024-0370 para `proc-macro-error 1.0.4`, executado na compilação por `ruststep-derive`. O uso do parser continua restrito ao ensaio da PRU-003. Essas exceções não autorizam ignorar uma vulnerabilidade nova.

Não há patch ou fork local das bibliotecas escolhidas. Atualizar SQLite, o binding ou ZIP exige repetir ensaios de falha, leitura hostil, concorrência, backup e reabertura, atualizar o inventário e examinar os avisos novos.

## 8. Ensaios isolados executados

O [fonte Rust reproduzível](../evidencias/PRU-005-bibliotecas-ensaio.rs) contém cinco ensaios. Todos passaram no Linux com a toolchain 1.99.1 e as features escolhidas:

| Ensaio | Referência e resultado observado |
|---|---|
| Nomes ZIP duplicados | Fixture binária construída diretamente dos campos da APPNOTE, sem usar `ZipWriter`: duas entradas idênticas resultam em `len() == 1`, mas `has_duplicate_names() == true` |
| Cabeçalhos ZIP divergentes | Fixture com nome local e central diferentes: leitura padrão aceita, opção de consistência recusa |
| Prefixo com offsets ajustados | Fixture binária com 9 bytes anteriores ao primeiro cabeçalho, incluídos nos offsets gravados: `offset() == 0` e consistência dos cabeçalhos válida; é necessária uma guarda adicional no perfil Prumo |
| WAL, rollback e backup | Estado literal evolui de revisão 1 para 2; tentativa de revisão 3 é revertida. Cópia bruta do banco ainda contém 1; backup pela API contém 2, passa em `integrity_check` e conserva 2 ao reabrir |
| Configuração defensiva | Flags são consultadas após configuração; tabela comum continua legível, enquanto uma view previamente criada deixa de ser executável |

Para reproduzir, copie o fonte para `src/lib.rs` de um projeto temporário, declare `[workspace]`, use as duas dependências fixadas do início desta ficha e `tempfile = "=3.27.0"`, e execute `cargo test` com a toolchain do repositório. O ensaio auxiliar não integra o runtime ou o workspace do produto. O lock principal continua sendo a referência da distribuição final.

Esses testes qualificam comportamentos das bibliotecas e decisões do adaptador. A aceitação completa ainda exige as falhas reais em processo, o pacote Prumo, migração, extensões, corrupção, versões futuras, igualdade dos hashes, interface/MCP e a matriz Windows/Linux previstos em [planning/issues/005.md](../../planning/issues/005.md). A auditoria de dependências acima já foi executada; não substitui essa aceitação funcional.
